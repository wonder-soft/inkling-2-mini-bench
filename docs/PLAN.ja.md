# 計測計画

公式の数値はすべて開発元が自分で計測したもの。ここでは**同じハーネス・同じタスクで、自分で測った数値だけ**を結論に使う。

比較先は2つ。Qwen3.8-27B（同じ RTX 5090 で Q4_K_M、[qwen3.8-27b-bench](https://github.com/wonder-soft/qwen3.8-27b-bench) の数値）と、Gemma 4 31B（OCR だけ新しく測る）。

## M0 — ハーネスが正しく動くか（モデルを評価する前に）

| # | 確認すること | 失敗したときに起きること |
|---|---|---|
| M0-1 | llama.cpp のビルドが b12611 以降か | 古いと NVFP4 のスケールが失われる。perplexity が約130 になり、「モデルが弱い」と誤って結論する |
| M0-2 | `reasoning_effort` が 0.0／0.2／0.9 で推論の長さを変えるか | 効いていないと、effort を変えて測っても何も測っていないことになる |
| M0-3 | 推論の中身が `reasoning_content` に分かれて入るか | 推論が `content` に漏れると、`### FILE:` の抽出が推論文を拾ってタスクが失敗する |
| M0-4 | tool_calls が返るか | 返らないと OpenCode が「推論はするが何もしない」状態になる |
| M0-5 | 画像を読めるか（`ocr/fixtures/smoke.png`） | mmproj の読み込み失敗を OCR の性能と取り違える |
| M0-6 | perplexity で量子化が壊れていないか（7.65 前後が目安） | 量子化の不具合をモデルの評価と取り違える |

## A. coding

| # | 計測 | 条件 |
|---|---|---|
| A1 | pass@1（n=5、ビルドとテストの両方が通ったら成功）。Go／Python／Rust (axum 0.8)／Scala (http4s) | effort 0.9、cab のサンプリング設定 |
| A2 | Rust の失敗の分類：借用、trait 境界、ライブラリの書き方、非同期、出力が空 | A1 の Rust 全サンプル |
| A3 | エラー修復ループ（コンパイラの出力を返し、最大3ラウンド）の収束ラウンド数 | Rust と Scala |
| A4 | tool の選択精度（n=30）、不正な tool 呼び出しの数、エージェントのエピソードの完了率 | — |
| A5 | effort を 0.0／0.2／0.7／0.9 と変えて A1 の Rust と Go を測る。上限を使い切った回数と、推論の文字数の分布も記録 | 推論のループ癖の定量化 |
| A6 | GGUF UD-Q4_K_M と、ネイティブの NVFP4（vLLM）の差 | vLLM がこのモデルに対応していれば |

## B. OCR（vision）

データは `ocr/gen_synthetic.py`（架空の帳票と青空文庫の文）と、ライセンスを確認した公開データセットだけを使う。**実在の書類は使わない。**

| # | 計測 | 指標 |
|---|---|---|
| B1 | 日本語の文字起こし（横書きの帳票・縦書きの文）× 劣化の程度 d0〜d3 | CER（NFKC 正規化、空白を除去） |
| B2 | 請求書から項目を抜いて JSON にする | 項目ごとの完全一致。明細は集合として一致するか |
| B3 | 表とチャート（Python ツールあり／なし） | 正答率 |
| B4 | 単体の vlm、単体の tesseract、hybrid（Tesseract の下書きと画像を一緒に渡す）の3条件 | CER、所要時間 |
| B5 | 画像の長辺を 768／1536／2480／4096px に変える | CER と所要時間 |
| B6 | effort を 0.0／0.2／0.9 に変える | CER と所要時間（OCR に推論は要るのか） |
| B7 | 比較：Qwen3.8-27B（mmproj）、Gemma 4 31B | 同じデータ・同じプロンプト |

## C. OpenCode での日常使い

| # | 計測 | 方法 |
|---|---|---|
| C1 | `bench/tasks/agent-*` と、公開 OSS でのシナリオ（バグ修正・機能追加・リファクタ・テスト追加）の完了率 | OpenCode に渡して `verify.sh` かテストで判定 |
| C2 | TTFT、デコード速度（tok/s）、1タスクの所要時間、ターン数 | `bench_throughput.py` と OpenCode のログ |
| C3 | 危険な操作：確認なしの削除・上書き、成功していないのに「完了」と報告した回数 | サンドボックス内で権限確認をオンにし、ログを人が確認する |
| C4 | 長いコンテキスト：32k／128k／256k／それ以上で速度と正答がどうなるか | 5090 で上限を探す。それ以上は PRO 6000 |
| C5 | 複数ターンの指示への追従（後から制約を足していく） | 手作りのシナリオ5本 |
| C6 | 1日分の作業として使ったときの所感 | 定性的な記録。上の数値と分けて書く |

## D. MacBook（M2 Pro 32GB）

| # | 計測 | 備考 |
|---|---|---|
| D1 | 量子化ごと（UD-Q4_K_M／UD-IQ3_XXS／MLX 4bit）のピークメモリと、載るかどうか | macOS の既定では GPU に回せるメモリが搭載量の一部に限られる。`iogpu.wired_limit_mb` を変えた場合は別の計測として区別する |
| D2 | prefill とデコードの tok/s（コンテキスト 4k／32k／128k） | `bench_throughput.py` |
| D3 | A1 の Rust と B1 の一部を再計測し、GPU サーバーとの差を見る | 量子化と Metal による劣化 |
| D4 | C1 のシナリオ2〜3本を Mac で動かす。電源接続時とバッテリー駆動時、発熱による速度低下 | 実用になるか |

## E. GPU サーバー

| 用途 | インスタンス | 理由 |
|---|---|---|
| A／B／C の本計測 | **RTX 5090 32GB ×1** | Qwen3.8-27B の数値と同じ条件。Blackwell 世代なので NVFP4 も動かせる |
| C4 の長いコンテキスト、A6 の vLLM | RTX PRO 6000 96GB ×1 | KV キャッシュの余裕 |

- ディスクはネットワークボリュームではなくローカルに置く（GGUF は mmap で読むため）。
- ポートは公開せず、SSH トンネルでつなぐ。
- 計測ごとに GPU 時間をレポートに記録する。

## 進める順番

M0 → A1/A5 → B1/B4 → D1/D2 → C1〜C3 → 残り
